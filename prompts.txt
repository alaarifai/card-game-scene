--------------------------------------------------------------------------------
1. APPROACH
--------------------------------------------------------------------------------

The project was developed through a two-person collaboration.
The responsibilities were divided into two main systems:

  Role A - hamza raweh:
    Room environment, floor, walls, ceiling, table, table zones,
    poster, and decorative objects.

  Role B - alaarifai:
    Playing cards, card class, cameras, keyboard interaction,
    card movement, and animation.

The development process followed these principles:

  1. Planning:
     Define the project requirements, divide responsibilities,
     establish shared scene coordinates and technical conventions.

  2. Understanding:
     Study the lecture code and understand the concepts before
     implementing new functionality.

  3. Implementation:
     Work on small, independent tasks (A1-A9 and B1-B9).

  4. Collaboration:
     Maintain shared technical constants and coordinate integration
     between the two development roles.

  5. Debugging:
     Investigate compilation, linking, rendering, texture, and
     camera-related problems.

  6. Verification:
     Build and run the application and compare actual results
     with the expected scene.

  7. Documentation:
     Record implementation decisions, important problems,
     and the concepts learned during development.

The main principle was to understand every important implementation
decision instead of simply accepting AI-generated code.

3. VERIFICATION OF AI OUTPUT
--------------------------------------------------------------------------------

All AI suggestions were treated as proposals and evaluated against
the actual project implementation.

Important verification cases included:

  - Camera positioning:
    The initial camera 2 position caused the standing deck to be
    clipped. The camera was reframed after checking projected
    coordinates.

  - Camera 1 height:
    The original height was increased from Y = 10 to Y = 11 after
    checking the field of view against the table dimensions.

  - Card stacking:
    The card offset was moved into local space to prevent z-fighting
    when cards stand vertically.

  - Shader loading:
    Incorrect runtime paths were investigated and corrected.
    The image appeared after the paths were fixed.

  - Texture loading:
    The texture loader was reviewed to support RGBA images,
    image flipping, and transparent textures.

  - White window crash:
    The actual Windows crash log was examined.
    The problem was traced to pixel unpack alignment for
    odd-width RGB images.

    The fix was:

      glPixelStorei(GL_UNPACK_ALIGNMENT, 1);

  - Ceiling visibility:
    Camera 1 was above the ceiling, which blocked the top view.
    The ceiling winding and face-culling behavior were corrected.

  - Runtime working directory:
    The program needed to run from the build directory because
    CMake copied the required assets there.

  - Window resizing:
    The projection aspect ratio was updated to prevent image stretching.

  - Texture updates:
    Updated assets did not appear until the executable was relinked
    because of the POST_BUILD asset-copy step.

  - Visual assets:
    Generated images were reviewed and improved when necessary.

  - Card illustrations:
    The first version was rejected and redesigned before acceptance.

  - Integration:
    Shared coordinates and object positions were checked to ensure
    compatibility between Role A and Role B.


--------------------------------------------------------------------------------
4. LESSONS LEARNED
--------------------------------------------------------------------------------

  - Dividing the project by system responsibilities makes
    collaboration easier.

  - Shared technical constants are important when different
    team members implement connected systems.

  - Understanding transformation order is essential for positioning
    and scaling objects correctly.

  - The transformation T * S scales an object first and then
    moves it to its required position.

  - Texture coordinates must be designed carefully to avoid
    stretching and incorrect orientation.

  - UV coordinates outside the range 0..1 can be used with
    GL_REPEAT to repeat textures.

  - Transparent textures require appropriate image loading
    and fragment shader handling.

  - Odd image widths may require GL_UNPACK_ALIGNMENT = 1.

  - Camera positioning and projection must be verified using
    actual scene dimensions.

  - An object between the camera and the scene can block the view
    and may require face culling or corrected geometry winding.

  - Local-space transformations are useful when an object must
    maintain its relative geometry during rotation.

  - deltaTime makes animations independent of frame rate.

  - Interpolation and smoothstep produce smoother movement.

  - Build errors, linker errors, and runtime errors must be
    investigated separately.

  - Relative file paths depend on the application's working directory.

  - Updated assets may require rebuilding or relinking depending
    on the CMake asset-copy configuration.

  - Small implementation steps make debugging and code review easier.

  - AI suggestions should always be tested against the actual
    application.

  - Understanding the reasoning behind every important line makes
    it easier to explain and maintain the final implementation.
